# Screenshot + Human Visual Checkpoint (필수 게이트, ★게이트 3)

> 이 게이트는 **감각적 한계(sensory limit)** 때문에 존재한다: LLM은 소스코드만으로 레이아웃 균형, 색 대비,
> 여백 리듬, 폰트 느낌을 신뢰성 있게 판단할 수 없다. 그래서 HTML 생성 후 **실제 브라우저에서 렌더하고,
> 스크린샷을 찍어, 사람에게 보여주고 사인오프를 받는다**. 이 게이트는 Simplified harness에서도
> **약화하거나 건너뛸 수 없다.** Evaluator는 자신이 읽은 스크린샷 기록과 사람 사인오프 기록 없이는 **PASS를
> 낼 수 없다.**
>
> 오케스트레이터 Step 4(렌더 + 스크린샷)와 Step 5(사람 비주얼 체크포인트)가 이 절차를 실행한다.

---

## 이 게이트가 영구적인 이유

다른 모든 하네스 컴포넌트는 모델이 강해질수록 제거 후보다(비타협 원칙 6, Evaluator 경계 개념). **이 게이트만은
예외다.** 컨텍스트나 계획의 한계가 아니라 *감각*의 한계를 보상하므로, 모델 업그레이드로 사라지지 않는다.
LLM이 여백이 숨 쉬는지, 대비가 편안한지 *볼* 수 없는 한, 사람이 렌더를 보는 단계는 영구적으로 필요하다.
"Evaluator가 처리한다"는 **허용되지 않는다** — Evaluator는 스크린샷을 읽어 보조할 뿐, *사람의 시각 사인오프*는
Evaluator가 대체할 수 없는 별도의 필수 단계다.

---

## Step 4 — 렌더 + 스크린샷 (기계) `[수행: 오케스트레이터]`

**agent-browser 스킬**(내장 브라우저 도구보다 우선)을 사용해 단일 HTML 파일을 실제 브라우저에서 렌더하고 증거를
캡처한다. Generator 라운드마다 **한 번** 수행한다(새 결함이 의심될 때만 재스캔 — 기계가 이미 본 것을 다시 보느라
사람을 기다리게 하지 않는다).

1. **파일 열기**: 실제 `file://` 경로에서 연다(동일 출처 fetch가 필요하면 로컬 서빙). **빌드 스텝 없이** 열려야 한다.
2. **2개 이상 뷰포트 폭에서 스크린샷**: 최소 모바일(~390px) 1개 + 데스크탑(~1280px+) 1개. **풀페이지(스크롤 포함)**로
   캡처해 모든 뉴스 카드가 증거에 담기게 한다(첫 화면만 찍지 말 것).
3. **인터랙션 실행** — generator_report.md "How to run / view"에 적힌 것들:
   - **다크모드 토글** 클릭 → 색 반전이 실제로 적용되는지
   - **카테고리 필터** 클릭 → 해당 카테고리만 남고 "전체"로 리셋되는지
   - **카드 hover** → hover 상태가 보이는지
   - 위를 수행하는 동안 **브라우저 콘솔 로그 캡처 — 목표는 에러 0**
4. **아티팩트 저장**: working_dir에 안정적 이름으로 — `screenshot-desktop.png`, `screenshot-mobile.png`,
   `console.log`. 경로를 기록한다(Evaluator의 감각-한계 probe에 필요).

agent-browser 스킬을 쓸 수 없는 환경이면 **게이트를 조용히 건너뛰지 말 것** — 사용자에게 브라우저 자동화가
불가함을 알리고 파일을 직접 열어 확인해 달라고 요청해, 사람 체크포인트(Step 5)는 그대로 일어나게 한다. 렌더 증거가
전혀 없는 산출물은 PASS 불가.

---

## Step 5 — 사람 비주얼 체크포인트 (사람 사인오프) `[수행: 오케스트레이터 ↔ 사용자]`

렌더 후 **결과를 사용자에게 제시하고 사인오프를 위해 멈춘다.** LLM이 판단할 수 없는 채널이다.

1. **렌더 결과 보여주기**: 데스크탑/모바일 스크린샷을 대화에 인라인(PNG를 Read)하거나, `open <file>`(macOS)로
   사용자 브라우저에서 열어 직접 스크롤하게 한다.
2. **집중 질문하기**, 예:
   > "렌더된 뉴스 다이제스트입니다(데스크탑/모바일). 시각적으로 괜찮나요 — 레이아웃 균형, 색 대비, 여백, 폰트
   > 느낌? 주제({topic_display})와 안 어울리거나 템플릿처럼 보이는 곳이 있나요? (예: 모든 주제에 똑같이 쓰는
   > 보라/파랑 그라디언트)"
3. **사인오프 기록**: `visual_signoff.md`에 승인자와 메모를 남겨 Evaluator가 인용할 수 있게 한다. 구체성 없는
   "괜찮아 보임"도 사인오프로 인정하되 그렇게 메모한다.
4. **사용자가 시각 문제를 지적하면 PASS 금지** — 문제를 다음 Generator 라운드의 Blocking Issue로 넣고
   Step 3 → 4 → 5를 재실행한다.

사람 사인오프(Step 5)와 주제 확정(Step 0)·spec 확인(Step 2)은 이 스킬의 필수 사용자 게이트다. 어느 것도 조용히
건너뛸 수 없다.

---

## Evaluator가 이 아티팩트로 하는 일

- **감각-한계 게이트 probe**: 스크린샷이 존재하고, Evaluator가 그것을 읽었으며(이미지에서 레이아웃 정렬·대비·여백·
  폰트 렌더링을 판단해 Visual Design Quality 채점에 반영), `visual_signoff.md`에 사람 사인오프가 기록되었는지
  확인한다. **셋 중 하나라도 없으면 PASS 불가(blocked).**
- **기술 무결성 probe**: 같은 렌더에서 인터랙션 중 **콘솔 에러 0**, 캡처한 2개 이상 폭에서 **레이아웃 깨짐 없음**,
  **유효한 시맨틱 HTML(미닫힘 태그 없음)**을 확인한다. 렌더된 DOM을 generator_report.md 주장과 교차 검증한다 —
  보고서만 믿지 말 것("필터가 실제로 동작하나, 아니면 CSS만 토글하나?").

## 빠른 체크리스트 (런 노트에 붙여넣기)

- [ ] HTML을 file 경로에서 빌드 스텝 없이 열었다
- [ ] 데스크탑 스크린샷 캡처(풀페이지)
- [ ] 모바일 스크린샷 캡처(풀페이지)
- [ ] 인터랙션(다크모드/카테고리 필터/hover) 실행, 콘솔 로그 캡처, **에러 0**
- [ ] 스크린샷을 인라인 / 파일을 사용자에게 열어줌
- [ ] 집중 질문으로 사용자에게 묻고 **사인오프 받음**(또는 문제 지적 → 다음 라운드)
- [ ] 스크린샷 경로 + 콘솔 로그 경로 + 사인오프(`visual_signoff.md`)를 Evaluator용으로 기록
